# Troubleshooting Notes 

## Issue 1 — `hostname.exe` Query Returned No Results

### Query

```esql
FROM logs-*
| WHERE process.name == "hostname.exe"
| KEEP @timestamp, host.name, user.name, process.pid, process.parent.name, process.parent.pid, process.command_line, process.executable
| SORT @timestamp DESC
```

### Result

```text
No results match your search criteria
```

### Investigation

The command had already been executed locally:

```powershell
cmd.exe /c hostname.exe
```

The command returned:

```text
DESKTOP-9MMM37V
```

However, Elastic did not return a standalone event where:

```text
process.name == "hostname.exe"
```

### Important Finding

A corresponding `cmd.exe` event was present:

```text
"C:\Windows\System32\cmd.exe" /c hostname.exe
```

Therefore, the investigation recorded the command-line evidence without claiming that a separate `hostname.exe` process event was captured.

### Lesson

Expected execution does not guarantee that every process will appear as an independently searchable event in the current telemetry dataset.

## Issue 2 — Parent-Process Query Produced Unrelated Results

### Query

```esql
FROM logs-*
| WHERE process.parent.name == "cmd.exe"
| KEEP @timestamp, host.name, user.name, process.name, process.pid, process.parent.name, process.parent.pid, process.command_line, process.executable
| SORT @timestamp DESC
```

### Result

```text
4 results processed
```

Some results included:

```text
conhost.exe
```

under:

```text
SYSTEM
```

### Investigation

The query correctly identified processes associated with `cmd.exe`, but not every returned event represented the controlled lab activity.

### Resolution

Controlled activity was separated using:

- Timestamp
- User
- Process ID
- Parent PID
- Command line
- Executable path

### Lesson

A parent-process filter identifies relationships, not necessarily the specific activity being investigated.

## Issue 3 — Broad Parent Query Returned Too Many Results

### Query

```esql
FROM logs-*
| WHERE process.parent.name IN ("cmd.exe", "powershell.exe", "pwsh.exe")
| KEEP @timestamp, process.name, process.pid, process.parent.name, process.parent.pid, process.command_line, user.name
| SORT @timestamp DESC
```

### Result

```text
181 results processed
```

### Investigation

The query successfully returned shell-related activity but produced a large dataset.

### Resolution

The investigation moved toward narrower filters using:

```text
process.name
```

and known command-line content.

Examples:

```esql
FROM logs-*
| WHERE process.name == "cmd.exe"
```

and:

```esql
FROM logs-*
| WHERE process.name == "whoami.exe"
```

### Lesson

Broad hunting is useful for discovery, but focused queries are usually more effective for validating a controlled lab event.

## Issue 4 — Broad Process Ancestry Query Returned a Large Dataset

### Query

```esql
FROM logs-*
| WHERE process.parent.name IS NOT NULL
| KEEP @timestamp, host.name, user.name, process.parent.name, process.name, process.parent.pid, process.pid, process.command_line, process.executable
| SORT @timestamp DESC
```

### Result

```text
705 results processed
```

### Investigation

This confirmed that process ancestry telemetry was available across the endpoint.

However, the large result set contained many unrelated relationships.

### Lesson

A broad process-tree query is useful for understanding endpoint activity, but event volume must be reduced through contextual filtering.

## Issue 5 — Distinguishing Controlled Activity from Existing Activity

The endpoint contained process activity that was not generated by the lab.

For example:

```text
updater.exe
    |
    +-- cmd.exe
```

The events occurred at:

```text
16:03:54.393
16:03:54.435
```

under:

```text
SYSTEM
```

and referenced:

```text
C:\Program Files\McAfee\WebAdvisor\
```

### Resolution

These events were kept separate from the controlled chain because they differed in:

- Timestamp
- Parent process
- User context
- Command line
- Purpose

### Lesson

Existing endpoint activity should not automatically be attributed to the current investigation.

## Issue 6 — Validating Parent-Child Relationships

The controlled `cmd.exe` activity showed:

```text
PID: 21172
Parent: pwsh.exe
Parent PID: 36120
```

The `whoami.exe` event was then reviewed to validate the child relationship.

This is stronger evidence than relying only on process names.

### Investigation Method

Validate relationships using:

```text
Parent Name
+
Parent PID
+
Child Name
+
Child PID
+
Timestamp
+
Command Line
```

### Lesson

Process ancestry should be reconstructed from multiple fields wherever possible.

## Issue 7 — Time Range Considerations

The investigation began with:

```text
Last 15 minutes
```

This was suitable for controlled activity because the commands were executed immediately before the searches.

When an expected event is missing, the next troubleshooting step is to expand temporarily to:

```text
Last 1 hour
```

and repeat the query.

This helps distinguish a telemetry issue from a time-window issue.

### Lesson

Always make sure the Elastic time range covers the actual execution timestamp.

## Issue 8 — Query Direction Matters

The following query:

```esql
WHERE process.name == "cmd.exe"
```

searches for `cmd.exe` itself.

The following:

```esql
WHERE process.parent.name == "cmd.exe"
```

searches for processes associated with `cmd.exe` as their parent.

These queries answer different questions.

### Investigation Model

```text
process.name
    ↓
What is this process?

process.parent.name
    ↓
What process launched this event?

process.parent.pid
    ↓
Which exact parent process instance was involved?
```

---

## Issue 9 — Command Line Can Contain Evidence Even When a Child Event Is Missing

The `hostname.exe` execution was not returned as a standalone process event.

However, the parent `cmd.exe` command line contained:

```text
/c hostname.exe
```

This provided useful evidence about the intended command execution.

### Lesson

When child-process telemetry is incomplete, command-line fields can provide supporting context, but they should not be treated as equivalent to a confirmed standalone child-process event.
